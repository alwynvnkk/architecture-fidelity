# Functionality and value

## Claims to behavior

Use the README to identify the proposition, then trace the important claims through public entrypoints, defaults, orchestration, persistence or external calls, and observable output. Inspect failures, recovery, and completion criteria where they affect the promised outcome.

Distinguish working default behavior, opt-in integrations, library-only components, prototypes, and documented plans. A module with tests may still be unreachable from production wiring. Conversely, a missing name or search hit does not establish missing behavior: search by responsibility and follow the owning flow.

Explain the main user journey in plain language. Separate the project's own contribution from behavior supplied by an underlying provider, framework, or CLI. Identify where the integration itself creates value through reduced coordination or stronger contracts.

## Value under realistic conditions

Assess who benefits, what existing workflow it replaces, and what new work it introduces. Consider setup, privileges, infrastructure, recurring spend, review effort, failure recovery, and maintenance burden only where they affect the decision. Broad feature count is not a substitute for a coherent usable path.

For benchmarks, inspect methodology and artifacts: measured or simulated, real or mock inputs, baseline, workload, quality definition, and included costs. Do not repeat headline gains as demonstrated savings when the evidence supports only a model or preview. Note honest disclosures and contradictory evidence.

Use the user's known workflow to assess fit. If it is unknown, make recommendations conditional on concrete use cases. Research current alternatives or external claims only when comparison is requested or necessary to substantiate the verdict; verify them with current primary sources. Do not manufacture a market comparison from memory.

Consider a small experiment when adoption value remains uncertain: identify the unresolved claim, representative workload, comparison baseline, and meaningful success measure. Avoid prescribing a pilot when a clear mismatch already answers the question.
